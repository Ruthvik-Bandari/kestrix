# Data handling and model guardrails policy

This policy covers the research track: building the benchmark, the baselines and any model training. It applies the plan's sections 11, 14 and 16 to the data we actually use. The shipped tool's runtime controls are covered in `docs/security-model.md`.

## 1. What data may be used

| Allowed | Not allowed |
| --- | --- |
| The pinned public sources in `sources.md`, under their licenses | Telemetry from any system you do not own or are not authorized to collect from |
| Synthetic events generated by repository scripts | Institutional, employer or client logs unless the owner gives written authorization |
| Lab captures from machines you own, in an isolated lab, with a written test plan | Personal data, credentials, regulated data (HIPAA, FERPA, PCI) |

Imported rules, logs and test definitions are untrusted data. They are parsed only through `kestrix.core.safe_load`, with size, depth and alias limits. Nothing in them is ever executed, evaluated or unpickled.

## 2. Where data lives

| Location | Contents | Lifetime |
| --- | --- | --- |
| `/scratch/$USER/kestrix/data/` on Explorer | Source checkouts, manifests, QC reports, intermediate files | Purged by Research Computing every month. Every source can be fetched again from its pin. |
| `/work/<group>/kestrix/` (if a PI allocation exists) | Frozen benchmark, split manifest, selected checkpoints | Persistent |
| This repository | Code, pins, docs and aggregate QC or evaluation reports | Versioned |
| Never in the repository or in Claude Code's working tree | Raw events, locked test inputs, checkpoints, tokens, passwords | n/a |

`data/raw/` and `data/locked/` are git-ignored. They are also denied to Claude Code by the project rules. Reports that leave the cluster are aggregates: counts, reason codes, rule IDs and file paths. Event field values never leave it.

Retention, per the plan: raw lab event captures are deleted after 30 days. Sanitized research evidence and aggregate reports are kept for as long as the source licenses allow.

## 3. Benchmark integrity guardrails

1. Each split is assigned by rule root (36 train, 12 development, 12 test) before any variant is generated. Related rule families and near-duplicates go into the same split. QC's `duplicate_detection_groups` lists the duplicate groups.
2. Split assignments and dataset hashes are frozen before training. The locked test set is read only by the final evaluation job, which reports aggregates only.
3. Training, prompt examples and retrieval indexes use training roots only. Tuning uses development roots only. Before every training run, root and hash overlap checks must find no overlap.
4. The pinned Elasticsearch replay is the only label oracle. An engine or conversion error is a failed run, never a negative prediction.
5. All cases, denominators, exclusions and failed runs are published with the results. No case is cherry-picked.

## 4. Model guardrails

- **Model choice:** only models with a recorded repository, revision, license and tokenizer. The license must allow research use; for any model we ship, it must also allow redistribution of weights or adapters.
- **Remote code:** never loaded automatically (`trust_remote_code=False`). Never load an unreviewed checkpoint.
- **Output:** the model only produces structured candidates within the candidate contract: at most 3 AST edits and 4 candidates, and it never drops a selection. It has no tools and no network access. Text inside rules or logs cannot trigger any action; adversarial fixtures test this.
- **Validation:** no candidate is accepted without replay validation on independent fixtures. Model scores are shown as scores, never as validated confidence.
- **Behavior:** abstention is a valid output. A model that repairs by weakening a rule fails the policy. Weakening means always-true, always-false, dropping a selection, or losing an attack scenario.
- **Release:** a model release ships with a model card, an evaluation report, its license and its manifest. A quantized or faster variant must show it keeps the repair behavior before it replaces another variant.

## 5. Compute use (Explorer cluster)

- Run work through Slurm. Never compute on login nodes; Research Computing terminates such jobs.
- Use the cluster only for Northeastern research or coursework. Never share accounts or credentials.
- Pick GPUs by task size; see `docs/hpc.md`. Measure before scaling up. Initial budget: 40 to 80 GPU hours.
- Publications that use the cluster include Research Computing's acknowledgement statement.

## 6. AI assistant boundary

Claude Code sends conversation content to Anthropic. It may read code, pins, docs and aggregate reports. It must not receive the following:

- credentials or tokens;
- raw institutional telemetry;
- locked test inputs;
- private evaluation data.

Cluster jobs write aggregate reports, and only those are reviewed in sessions.

**Exception, approved by the owner on 2026-10-16:** the OTRF review packet may be labeled by AI reviewers in a Claude Code session. That data is public lab recordings, not institutional telemetry. The labels carry `ai-` reviewer provenance and are reported separately, and a human checks every adjudicated label plus a 10% sample before the split is frozen ([`review.md`](review.md)). The exception does not cover institutional data, credentials or locked test results.

**Second exception, requested by the owner on 2026-10-20 (owner to confirm):** the label audit of the code-vulnerability pool (C5) may also be done by AI reviewers in a Claude Code session, following the same two-reviewer procedure ([`review.md`](review.md#ai-assisted-audit-of-the-code-vulnerability-labels)). The code is public open-source code and the advisories are public. The differences from the OTRF exception:

- the owner decided that a human review is not practical, so no human checks the AI verdicts; every result built on them says "AI-assisted";
- only train and dev records are audited. The frozen test split and the test extension are locked test inputs and are never sent to a session;
- packets stay in a private folder outside the repository (0700, files 0600) and on the cluster; the repository gets aggregates and ids only;
- per-record verdicts are evaluation metadata, never training labels or a training-record selector, so plan principle 3 (no labels generated by commercial models) still holds. Only the aggregate per-stratum accuracy may decide a rule-level filter (for example, leaving out a labelling rule that proves noisy).

## 7. Lab testing (Atomic Red Team)

Running a test, as opposed to reading its definition, requires all of the following:

- a machine you own, isolated from production and from other people's networks;
- a written plan listing the technique IDs, the machine and a time window;
- an allowlist of the tests to run;
- a capture of the resulting telemetry, labeled `lab_introduced`.

No test is run against shared university infrastructure.
