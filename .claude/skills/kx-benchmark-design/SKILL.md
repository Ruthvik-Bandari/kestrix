# Benchmark and grouped split design

Plan refs: sections 2 (10 failure cases), 7 (FailureCase, DatasetVersion), 11 (all), 13, 16 (benchmark leakage).

## Expected inputs

- Candidate roots: clean rule plus scenario, with source URL, revision and license.
- Impairment variants: field rename or type change, noisy predicate, selection logic fault, missing telemetry.
- Existing split manifest and its hash, if any.

## Steps

1. Assign each root to train / dev / locked before generating variants (target 36 / 12 / 12 of 60 roots). Group near-duplicate rules and rule families into one root group.
2. All variants, healthy versions, prompt examples and generated candidates from a root inherit the root's split.
3. Record per source: URL, commit, license, allowed use, capture method, collection date.
4. Record per event: malicious / benign / unknown, scenario ID, rule relevance, reviewer rationale. A suspected FP needs a reviewed benign label.
5. Record fault provenance: natural, lab introduced or synthetic. Results are later reported per stratum.
6. Write a leakage check: no root ID, rule hash or near-duplicate rule text appears in more than one split; fail on overlap.
7. Freeze split manifest and dataset hashes. Locked inputs live outside this working tree; only their hashes and IDs appear here.
8. Plan a second held-out schema for cross-environment testing.

## Output evidence

- Split manifest with hashes, leakage check output, label and license table, counts per split and provenance.
- Explicit statement of counts actually acquired versus planning targets.

## Failure conditions (stop and report)

- Grouping leaves too few roots: report and propose reducing scope; do not split a root.
- A request to move a root between splits after test results are seen.
- Labels would be generated by the model being evaluated.
